# AMOS 2026 Space-Based Reimaging Architecture

This branch is for the AMOS 2026 space-based imaging/reimaging paper direction:
fast retasking, variable-duration imaging and downlink actions, target reappearance,
and the next step toward uncertainty-aware reobservation.

## Branch Baseline

- Source branch: `IA_Polaris_imaging_june10`.
- AMOS branch: `amos-2026-space-imaging`.
- The branch was created from the current imaging-June-10 working tree, including the
  10-second pointing hold gate, two-orbit reimage cooldown, eligibility-based target
  lists, and priority generation/rescaling work.
- `examples/policy_evaluation_2026.py` and `examples/updated_policy_evaluation.py`
  now default to variable-duration imaging for the AMOS branch.
- Downlink actions now have an optional variable-duration mode that can stop early when
  storage reaches zero while preserving the old fixed-duration behavior as the action
  class default.

## Current Code Map

- `src/bsk_rl/act/discrete_actions.py`
  - `ImageRSO` selects eligible RSO targets and can terminate early after a successful
    hold-gated image.
  - `ImageRSO` checks access, attitude error, and optional rate error during the hold

    onboard success/failure.
  - `ImageRSO` stages capture metadata including first-capture illumination and mean
    hold illumination for the datastore.
  - `Downlink` can optionally terminate early when storage is empty.
- `src/bsk_rl/data/rso_targets_data.py`
  - `RSOTargetImageData` stores all known targets, verified imaged targets, pending

  - `RSOTargetImageReward` estimates the scanner orbit period and converts
    `reimage_cooldown_orbits` into seconds.
  - With `verify_image_quality_on_downlink=True`, reward is granted only after downlink
    verification; useful-image cooldown is then scheduled from the original capture time.
  - The current default cooldown in `examples/sim_config.py` is two scanner orbits.
- `src/bsk_rl/obs/observations.py`
  - RSO observations use the same eligibility lifecycle as the action selection.
- `src/bsk_rl/scene/rso_targets.py`
  - Target priorities can be generated by `uniform`, `gaussian`, or `constant` modes.
  - If `rescale_priorities_to_sum=True`, priorities are rescaled before the first

    correction.
- `examples/sim_config.py`
  - Shared knobs for imaging duration, hold gate, reimage cooldown, target priorities,

## Current Reimaging Lifecycle

The current implementation is eligibility-based, not a permanent imaged/unimaged split.

1. At reset, all targets are known and eligible because `cooldown_until_by_id` is empty.
2. `ImageRSO` and `PolarisScTargetProperties` filter target candidates through
   `eligible_targets(sim_time, known_targets)`.
3. Eligible targets are sorted by visibility/elevation and padded by closest eligible
   targets if fewer than `n_targets_ahead` are visible.
4. A new image is detected by an increase in the corresponding target storage partition.
5. With `verify_image_quality_on_downlink=True`, the datastore creates a
   `pending_verification` record even if illumination is below the image-quality
   threshold.
6. Pending targets are hidden from the action/observation eligible list when
   `hide_pending_targets=True`.
7. Downlink is detected by a decrease in the corresponding target storage partition.
8. If the pending image's mean hold illumination passes the quality threshold, reward is
   granted and cooldown is anchored to the original capture time.
9. If the pending image fails quality verification, the pending state is cleared and the
   target becomes eligible immediately with no cooldown.
10. `cooldown_until = capture_time + reimage_cooldown_s`, where
   `reimage_cooldown_s = reimage_cooldown_orbits * estimated_scanner_orbit_period_s`.
11. If the image is downlinked after that deadline has already passed, the target is
   immediately eligible again after verification.
12. Once the simulation time passes the cooldown deadline, the target automatically
   becomes eligible again.

Legacy behavior is still available by setting `verify_image_quality_on_downlink=False`.
In that mode, the older capture-time image/reward/cooldown path is used. To recover
the older illumination-gated action behavior as well, set
`require_illumination_during_hold=True`.

## Current Hold-Gate Semantics

`ImageRSO` uses a hold-gated event evaluated at the FSW rate:

- The event is scheduled with `macros.sec2nano(self.satellite.fsw.fsw_rate)`.
- The evaluation scripts currently do not pass `sim_rate`, so `GeneralSatelliteTasking`
  defaults to `sim_rate=1.0` seconds. That means the dynamics, FSW, and hold-gate event
  cadence are currently 1 Hz in the Python evaluation scripts.
- If we want the paper statement "FSW update at 2 Hz" to match this branch, we should set
  `sim_rate=0.5` explicitly in the AMOS evaluation/training constructors.
- Hold valid time accumulates when access, attitude, and optional rate constraints are
  satisfied. If `require_illumination_during_hold=True`, illumination is also required
  for the legacy onboard-quality behavior.
- The average illumination is computed as an average over accumulated valid hold time.
- The current implementation can include valid pointing time accumulated immediately
  before the first storage increase is observed. With the current cadence, this is at
  most one FSW event interval of ambiguity.

## Current Image-Quality Assumption

The AMOS default now implements the "onboard does not know image quality until downlink"
assumption:

- Onboard capture success is based on pointing/access/hold, not on final image quality.
- The image is stored as pending verification.
- The target is not immediately available for repeated retasking while its image is
  pending downlink verification.
- At downlink, the ground/handshake determines whether the image was useful.
- If useful, reward is granted and the target enters the reimage cooldown.
- If not useful, the target becomes eligible immediately, with no cooldown delay.

The actual quality test uses `mean_hold_shadow_factor` when available, falling back to
`capture_shadow_factor` if hold-average metadata is not available.

Relevant config flags:

- `verify_image_quality_on_downlink`: enables pending/downlink verification.
- `hide_pending_targets`: removes pending targets from action/observation eligibility.
- `image_quality_threshold`: overrides the default image-quality threshold.
- `require_illumination_during_hold`: restores legacy onboard illumination gating when
  needed.

## Implemented Handshake State Machine

The lifecycle states are:

- `eligible`: target can be selected for imaging.
- `pending_verification`: onboard believes an image was captured, but ground has not
  acknowledged quality yet.
- `cooldown`: a verified-useful image was downlinked; target is hidden until cooldown
  expires.

Each pending image record includes:

- `target_id`
- `target_name` / storage partition name
- `capture_time`
- `capture_shadow_factor`
- `mean_hold_shadow_factor`
- `hold_valid_time_s`
- `storage_delta_bits`
- `source_satellite`
- `verification_status`

Downlink verification maps storage decreases back to pending image records by the target
storage partition name. Only partitions whose stored-data value decreases are processed,
so a partial downlink does not verify unrelated targets that remain in the buffer.
Pending records are kept in per-target queues. If we later allow multiple images of the
same target to be captured before downlink, adding unique image packet IDs would make
that mapping more physically explicit.

## Dynamic Downlink Behavior

Implemented in this branch:

- `Downlink(..., variable_duration_downlink=True)` creates an early-stop event.
- The event triggers when `satellite.dynamics.storage_level <= empty_storage_threshold_bits`.
- The configured `duration` remains the maximum downlink duration.
- `examples/sim_config.py` defaults AMOS runs to `variable_duration_downlink=True`.

`examples/updated_train_Polaris.py`. It has the newer `SimConfig` wiring, WGAE PPO
learner, cluster temp-directory notes, and Jan/cluster-style result naming.

Current AMOS training defaults in that script:

- `alpha=0.2` legacy reward split fields (`downlink_bonus=0.2`,
  `imaging_bonus=0.8`). With downlink verification enabled, the useful-image reward is
  delayed to the verified downlink event.
- Target priorities are generated through `SimConfig` and `RandomSatellites`; by
  default, they are uniform and rescaled so the per-episode priority sum is exactly
  `100`.
- Added callback metrics include total/useful/failed downlinks, pending images, verified
  reimages, average chosen/attempted/verified target priority, and average actual
  imaging-action duration.

Remaining validation:

- Run at least one short evaluation and confirm `info["d_ts"]` is shorter than 180/300
  seconds when storage drains early.
- Confirm a downlink action with empty storage returns control after one simulation event
  cadence rather than burning the full action duration.
- Confirm no stale downlink-empty event can stop a later non-downlink action.

## AMOS 2026 Implementation Plan

1. Lock the AMOS evaluation cadence.
   - Decide whether the paper should use 1 Hz or 2 Hz.
   - If 2 Hz, set `sim_rate=0.5` explicitly in the AMOS evaluation/training constructors.
2. Validate pending/downlink verification in a short deterministic scenario.
   - Confirm dark images become pending and then immediately eligible after failed
     downlink verification.
   - Confirm useful images become pending and then enter capture-anchored cooldown after
     downlink.
   - Confirm pending targets are not exposed to the policy.
3. Improve physical downlink packet mapping if needed.
   - Current mapping uses target partition decreases.
   - A future unique image packet ID would disambiguate repeated same-target captures
     before downlink.
4. Keep dynamic downlink optional but enabled for AMOS experiments.
   - Preserve fixed-duration downlink for backward comparisons.
5. Create an AMOS-specific experiment structure.
   - Put new paper scripts under `examples/amos_2026/`.
   - Keep reusable config/metrics helpers separate from one-off plotting notebooks.
6. Add validation tests/plots.
   - Tests for cooldown timing, pending bad-image immediate re-eligibility, priority sum,
     and early downlink termination.
   - Metrics for useful downlinks, failed downlinks, reimages, cooldown waits, and
     actual action durations.

## Uncertainty-Aware Reimaging Roadmap

The next research extension is to make reimaging valuable because it reduces target
state uncertainty, not only because a cooldown expired.

Minimal version:

- Track a scalar uncertainty or "age of information" per target.
- Let uncertainty grow with time since last verified image.
- Make required imaging/search duration increase with uncertainty.
- Reward verified images by uncertainty reduction.

Medium version:

- Track a 2D or 3D covariance per target.
- Propagate with a simple linear dynamics model and process noise.
- On verified image, perform a measurement update or reset to a measurement covariance.
- Reward by information gain, for example `log(det(P_prior)) - log(det(P_post))`.

Full paper-grade search-area version:

- Convert covariance into a search ellipse/volume in the sensor frame.
- Compute the effective sensor footprint/FOV at target range.
- Estimate search time from area-to-cover divided by sensor sweep/brush rate.
- Let the imaging action duration be `slew_time + search_time + confirmation_hold`.
- Use the reward to value uncertainty reduction, not just target priority.

Effort estimate:

- Scalar uncertainty prototype: 2-4 focused days.
- Covariance/EKF-style model with observations and metrics: 1-2 weeks.
- Search-area brush model with FOV geometry, validation plots, and ablations: 3-6 weeks.

## Key Modeling Choices To Decide

- Should cooldown be scheduled at capture time or downlink acknowledgment time? Current
  AMOS behavior schedules it at capture time, but only after useful downlink
  acknowledgment proves the image was useful.
- While a captured image is pending downlink, should the target be hidden from imaging?
  Prefer yes, unless we are modeling deliberate redundant imaging.
- Should failed/dark images generate a penalty, zero reward, or only opportunity cost?
- Do we allow multiple pending images per target before downlink? If yes, we need queues
  or unique image packet IDs.
- Should onboard know target illumination well enough to avoid dark captures, or should
  illumination be hidden/noisy and verified only on the ground?
